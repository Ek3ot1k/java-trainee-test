# Code Review

Представьте, что код из каталога `code-review/` пришёл в обычном Pull Request от другого разработчика. Он реализует упрощённое создание и чтение заказа. Вы — reviewer, которому нужно решить, можно ли отправлять этот код в production.

На review рекомендуется потратить около **20–30 минут**. Запускать или переписывать код не обязательно.

Подготовьте Markdown-файл с результатом review. Для каждого замечания укажите:

- где находится проблема;
- почему это проблема;
- к чему она может привести;
- как вы предложили бы её исправить.

Разделите замечания примерно на:

- **Critical** — риск некорректных денег/остатков, потери целостности или серьёзного production-инцидента;
- **Major** — неверное поведение, плохой API-контракт или существенная проблема сопровождения;
- **Minor** — улучшение, которое полезно, но само по себе не блокирует релиз.

Не нужно найти заранее заданное количество проблем и не нужно комментировать каждую строку. Приоритет — реальные последствия, а не вкусовые предпочтения.

В конце ответьте на вопрос:

> Что в этом коде сделано нормально и вы бы не стали менять без дополнительной причины?

Если для вывода не хватает контекста, явно назовите предположение или вопрос автору PR.
