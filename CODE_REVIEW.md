# Code Review

Ниже перечислены проблемы, которые я бы попросил исправить до merge.

## Critical

### 1. Цена товара берётся из запроса клиента

**Где:** `CreateOrderRequest.Item.unitPrice`, `OrderService.create()`.

Сейчас клиент сам передаёт `unitPrice`, и именно это значение сохраняется в `OrderItem`. При этом у `Product` уже есть актуальная цена из каталога.

Клиент может передать неправильную, нулевую или отрицательную цену. В результате сумма заказа будет рассчитана неверно.

**Как исправить:** убрать `unitPrice` из запроса и при создании `OrderItem` использовать `product.getPrice()`. Цена из базы должна сохраняться в заказе как snapshot цены на момент покупки.

---

### 2. Создание заказа не выполняется в одной транзакции

**Где:** `OrderService.create()`.

Заказ сохраняется до начала обработки товаров:

```java
CustomerOrder order = orderRepository.save(new CustomerOrder());
```

После этого остатки товаров изменяются по одному. Если во время обработки одной из следующих позиций произойдёт ошибка, часть изменений уже может остаться в базе.

Это нарушает требование атомарности: заказ должен либо создаться полностью, либо не создаться вообще.

**Как исправить:** выполнять весь метод создания заказа в одной транзакции с `@Transactional`. При ошибке исключение должно выходить из метода, чтобы Spring откатил все изменения.

Также стоит добавить интеграционный тест, который проверяет rollback остатков при ошибке на одной из позиций.

---

### 3. Исключения внутри цикла подавляются

**Где:** `OrderService.create()`.

Весь код обработки позиции находится внутри:

```java
catch (RuntimeException exception) {
    System.out.println("Skipping item " + requestedItem.productId());
}
```

Из-за этого ошибочная позиция просто пропускается, после чего заказ продолжает создаваться.

Например, если одна из трёх позиций недоступна, клиент всё равно может получить успешный заказ только с двумя позициями. Это противоречит требованию: если хотя бы одну позицию нельзя обработать, весь заказ должен быть отменён.

Кроме бизнес-ошибок такой `catch` может скрыть и другие `RuntimeException`, включая ошибки приложения или инфраструктуры.

**Как исправить:** не подавлять исключение. Ошибка обработки любой позиции должна прерывать создание заказа и приводить к rollback транзакции. Ловить исключение стоит только там, где есть конкретная стратегия восстановления.

---

### 4. Возможна race condition при изменении stock

**Где:** `OrderService.create()`.

Сейчас выполняется последовательность:

```java
Product product = productRepository.findById(...).get();

if (product.getStock() < requestedItem.quantity()) {
    ...
}

product.setStock(product.getStock() - requestedItem.quantity());
productRepository.save(product);
```

Два параллельных запроса могут одновременно прочитать одинаковый остаток и оба пройти проверку. Это может привести к продаже большего количества товара, чем реально есть на складе.

Обычного `@Transactional` недостаточно, чтобы полностью решить эту проблему.

**Как исправить:** использовать одну из стратегий конкурентного обновления:

- optimistic locking через `@Version`;
- pessimistic write lock;
- атомарный SQL update с условием, что остатка достаточно.

Конкретный вариант зависит от требований к нагрузке и конкурентности.

## Major

### 5. Нет валидации входного запроса

**Где:** `CreateOrderRequest`, `OrderController`, `OrderService`.

Не проверяются:

- `items == null`;
- пустой список товаров;
- `productId == null`;
- `quantity <= 0`.

Особенно опасно отрицательное количество. Например, при `quantity = -5` выражение:

```java
product.setStock(product.getStock() - requestedItem.quantity());
```

увеличит остаток товара вместо уменьшения. Также итоговая стоимость позиции станет отрицательной.

**Как исправить:** добавить Bean Validation (`@NotNull`, `@NotEmpty`, `@Positive`, `@Valid`) и использовать `@Valid` в контроллере. Критичные бизнес-инварианты также желательно проверять на уровне сервисной или доменной логики.

---

### 6. Не определено поведение для одинаковых productId

**Где:** `OrderService.create()`.

Клиент может передать один товар несколько раз:

```json
{
  "items": [
    {
      "productId": 1,
      "quantity": 2
    },
    {
      "productId": 1,
      "quantity": 3
    }
  ]
}
```

Сейчас каждая строка будет обработана отдельно. Это делает поведение API неоднозначным и усложняет корректную проверку общего количества товара.

**Как исправить:** выбрать явную политику: либо запрещать повторяющиеся `productId`, либо сначала объединять их и проверять суммарное количество. Выбранное поведение стоит зафиксировать в API-контракте.

---

### 7. Некорректная обработка HTTP-ошибок

**Где:** `OrderService`, `OrderController`.

Для получения товара используется:

```java
productRepository.findById(requestedItem.productId()).get();
```

Если товара нет, будет выброшен `NoSuchElementException`.

При запросе отсутствующего заказа также может быть выброшен `NoSuchElementException`. Явной обработки этих исключений в REST API нет, поэтому клиент может получить `500 Internal Server Error` вместо понятного `404`.

Кроме того, успешное создание заказа сейчас возвращает `200 OK`:

```java
ResponseEntity.ok(orderService.create(request))
```

Для создания нового ресурса логичнее вернуть `201 Created`.

**Как исправить:** использовать отдельные бизнес-исключения, например `ProductNotFoundException`, `InsufficientStockException`, `OrderNotFoundException`, и обрабатывать их через `@RestControllerAdvice`.

---

### 8. JPA entity напрямую используется как модель REST API

**Где:** `OrderController`.

Контроллер напрямую возвращает `CustomerOrder`:

```java
ResponseEntity<CustomerOrder>
```

Таким образом REST-контракт становится связан с persistence-моделью.

Изменение entity может случайно изменить API. Также появляются риски с lazy relations, сериализацией лишних полей и необходимостью добавлять Jackson-аннотации прямо в JPA entity.

**Как исправить:** использовать отдельные response DTO, например `OrderResponse` и `OrderItemResponse`, и явно преобразовывать entity в DTO внутри service/use case.

---

## Minor

### 9. Используется System.out вместо нормального логирования

**Где:** `OrderService.create()`.

```java
System.out.println("Skipping item " + requestedItem.productId());
```

`System.out` плохо подходит для серверного приложения: нет уровня логирования, структурированного контекста и нормальной интеграции с системой логов.

При этом исходная причина исключения сейчас теряется.

**Как исправить:** основное исправление — не подавлять исключение. Если логирование действительно необходимо, использовать SLF4J/logger и сохранять полезный контекст.

---

## Что сделано нормально

В коде есть решения, которые я бы не стал менять без дополнительной причины:

- используется constructor injection;
- controller, service и repository разделены;
- для денежных значений используется `BigDecimal`, а не `double`;
- используется Spring Data `JpaRepository`;
- `CustomerOrder` агрегирует свои `OrderItem` через `addItem()`;
- в `OrderItem` сохраняются `productId` и `productName`, поэтому часть данных о товаре фиксируется на момент создания заказа;
- название `CustomerOrder` удачнее, чем просто `Order`, которое может конфликтовать с SQL-терминологией.

В текущем виде я бы не отправлял этот PR в production. В первую очередь необходимо исправить источник цены, транзакционность и подавление исключений. После этого — валидацию, HTTP-ошибки и конкурентное изменение остатков.
