# Задание: мини-сервис создания заказа

## Контекст

Покупатель marketplace выбирает товары и отправляет состав заказа. Сервис должен проверить актуальные данные товаров в базе, рассчитать стоимость и сохранить заказ.

Нужно реализовать REST API на Java 21 и Spring Boot 3 с PostgreSQL.

Ожидаемый результат — самостоятельный запускаемый проект, а не только набор отдельных классов. По инструкции из README интервьюер должен суметь поднять приложение, применить миграции, вызвать API и запустить тесты.

## Данные товара

Минимально товар содержит:

- `id`;
- `name`;
- `price`;
- `stock` — доступное количество;
- `available` — разрешена ли продажа.

Выберите подходящий тип данных для денежных значений и объясните выбор.

## Создание заказа

Реализуйте endpoint создания заказа. URI и точный формат успешного ответа выберите сами и опишите в README.

Пример входного запроса:

```json
{
  "items": [
    { "productId": 1, "quantity": 2 },
    { "productId": 4, "quantity": 1 }
  ]
}
```

Система должна:

1. Получить актуальные товары из базы.
2. Убедиться, что каждый товар существует и доступен для продажи.
3. Проверить запрошенное количество и остаток.
4. Рассчитать стоимость каждой позиции и заказа целиком. Цена из запроса клиента не является источником истины.
5. Уменьшить остатки.
6. Создать заказ и его позиции. В позиции заказа должна сохраниться цена, по которой товар был заказан.
7. Вернуть результат с идентификатором, позициями и итоговой стоимостью.

Заказ должен создаваться **атомарно**: если одна из операций завершается ошибкой, частично созданного заказа и частично уменьшенных остатков быть не должно.

## Получение заказа

Реализуйте:

```http
GET /orders/{id}
```

Endpoint возвращает созданный заказ с позициями и итоговой стоимостью. Для отсутствующего заказа верните осмысленный HTTP-ответ.

## Обязательные случаи

Решение должно корректно вести себя, если:

- `productId` не существует;
- товар недоступен (`available = false`);
- остатка недостаточно;
- `quantity` равен нулю или меньше нуля;
- `items` пустой или `null`;
- один `productId` встречается несколько раз.

Для повторяющегося `productId` вы можете отклонить запрос или объединить количество. Это решение намеренно не задано: примите его осознанно, опишите в README и будьте готовы объяснить последствия.

Ошибочный запрос не должен приводить к частичному изменению данных. Выберите разумные HTTP status codes и понятный формат ошибки.

## Автоматические тесты

Нужны минимум три автоматических теста:

1. успешное создание заказа;
2. отказ при недостаточном остатке;
3. отказ при отсутствующем товаре.

Форма тестов — unit, integration или разумная комбинация — остаётся за вами. Дополнительные осмысленные тесты будут плюсом, но большой процент coverage не является целью.

## Технические рамки

- Java 21;
- Spring Boot 3;
- Maven или Gradle;
- Spring Data JPA / Hibernate;
- PostgreSQL;
- Liquibase для схемы БД;
- REST API;
- JUnit 5; Mockito и Testcontainers можно использовать там, где они помогают.

OpenAPI и MapStruct допустимы, но не обязательны. Не добавляйте Kafka, Redis, Kubernetes, микросервисы, OAuth или сложный Spring Security.

## Граница задания

Не нужно реализовывать пользователей, оплату, доставку, скидки, полноценный каталог или административную панель. Цель — небольшой, понятный и консистентный сценарий заказа.

На интервью будьте готовы пошарить экран, запустить проект и своими словами показать, как запрос проходит от REST endpoint до базы данных. Мы не ждём заученной презентации — важно, чтобы вы понимали и могли объяснить собственное решение.
