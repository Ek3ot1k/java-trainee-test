# Order Test Service

Небольшой REST-сервис для создания и получения заказов.

## Стек

* Java 21
* Spring Boot 3
* Spring Data JPA / Hibernate
* PostgreSQL
* Liquibase
* Maven
* JUnit 5
* Testcontainers

## Запуск приложения

### Требования

Для запуска нужны:

* Java 21
* Docker
* Maven

Запустить PostgreSQL:

```bash
docker compose up -d
```

Запустить приложение:

```bash
mvn spring-boot:run
```

Приложение будет доступно по адресу:

```text
http://localhost:8080
```

При запуске Liquibase автоматически применяет миграции базы данных.

Также миграции добавляют несколько тестовых товаров, которые можно использовать для проверки API.

## Запуск тестов

Docker должен быть запущен, так как интеграционные тесты используют PostgreSQL через Testcontainers.

```bash
mvn test
```

Тестами покрыты:

* успешное создание заказа;
* уменьшение остатков товара;
* недостаточное количество товара;
* отсутствие товара;
* недоступный товар;
* повторяющиеся `productId`;
* получение заказа;
* откат изменений при ошибке внутри транзакции;
* основные ошибки HTTP API.

## API

### Создание заказа

```http
POST /orders
```

Пример запроса:

```json
{
  "items": [
    {
      "productId": 1,
      "quantity": 2
    },
    {
      "productId": 2,
      "quantity": 1
    }
  ]
}
```

Пример ответа:

```json
{
  "id": 1,
  "items": [
    {
      "productId": 1,
      "quantity": 2,
      "price": 79.99,
      "subtotal": 159.98
    },
    {
      "productId": 2,
      "quantity": 1,
      "price": 39.50,
      "subtotal": 39.50
    }
  ],
  "total": 199.48
}
```

Цена товара всегда берется из базы данных.

Клиент не передает цену товара в запросе.

При создании заказа текущая цена товара сохраняется в `order_items`. Поэтому изменение цены товара в будущем не изменит стоимость уже созданного заказа.

### Получение заказа

```http
GET /orders/{id}
```

Пример:

```bash
curl http://localhost:8080/orders/1
```

Если заказ не существует, API возвращает:

```http
404 Not Found
```

Пример ответа:

```json
{
  "code": "ORDER_NOT_FOUND",
  "message": "Order 999 not found"
}
```

## Валидация и бизнес-правила

При создании заказа проверяется следующее:

* `items` не должен быть `null`;
* список `items` не должен быть пустым;
* элементы внутри `items` не должны быть `null`;
* `productId` не должен быть `null`;
* `quantity` должен быть больше `0`;
* товар должен существовать;
* товар должен быть доступен;
* товара должно быть достаточно на складе;
* одинаковый `productId` нельзя передавать несколько раз.

Повторяющиеся `productId` отклоняются с ошибкой.

Я выбрал такой вариант вместо объединения одинаковых позиций, чтобы контракт API оставался однозначным, а проверка остатков была проще и понятнее.

## Транзакционность

Создание заказа выполняется внутри одной транзакции.

При обработке заказа уменьшаются остатки товаров.

Если при обработке одной из следующих позиций возникает ошибка, все предыдущие изменения откатываются, а заказ не создается.

Это поведение отдельно проверяется интеграционным тестом на реальной PostgreSQL через Testcontainers.

## Работа с денежными значениями

Для хранения и расчетов денежных значений используется `BigDecimal`.

`double` и `float` не используются, так как двоичная floating-point арифметика может приводить к ошибкам точности при работе с деньгами.

В PostgreSQL денежные значения хранятся в колонках типа:

```text
DECIMAL(19,2)
```

## Структура базы данных

Основные таблицы:

```text
products
orders
order_items
```

`order_items` хранит:

* товар;
* количество;
* цену товара на момент создания заказа.

Схема базы данных управляется через Liquibase.

## Структура проекта

```text
controller/   REST-контроллеры
dto/          модели запросов и ответов
entity/       JPA-сущности
exception/    исключения и обработка ошибок API

service/      бизнес-логика
```

## Ограничения текущего решения

Текущая реализация явно не защищает изменение остатков от конкурентного создания заказов.

Например, две параллельные транзакции теоретически могут одновременно прочитать один и тот же остаток товара до фиксации изменений.

В production-решении для этого можно использовать:

* pessimistic locking;
* optimistic locking через `@Version`;
* атомарный SQL update с проверкой остатка.

В рамках тестового задания дополнительная concurrency-логика не добавлялась, чтобы не усложнять основную реализацию.
