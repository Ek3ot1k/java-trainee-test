# Order Test Service

Небольшой REST-сервис для создания и получения заказов.

## Стек

- Java 21
- Spring Boot 3
- Spring Data JPA / Hibernate
- PostgreSQL
- Liquibase
- Maven
- JUnit 5
- Testcontainers

## Как запустить приложение

### Требования

Для запуска нужны:

- Java 21
- Maven
- Docker

### 1. Перейти в каталог приложения

Если вы находитесь в корне репозитория:

```bash
cd starter
```

### 2. Запустить PostgreSQL

```bash
docker compose up -d
```

### 3. Запустить приложение

```bash
mvn spring-boot:run
```

После запуска приложение будет доступно по адресу:

```text
http://localhost:8080
```

Liquibase автоматически создаёт структуру базы данных и добавляет несколько тестовых товаров.

## Как запустить тесты

Docker должен быть запущен, так как интеграционные тесты используют PostgreSQL через Testcontainers.

```bash
mvn clean test
```

Тестами покрыты:

- успешное создание заказа;
- уменьшение остатков товара;
- недостаточное количество товара;
- отсутствие товара;
- недоступный товар;
- повторяющиеся `productId`;
- получение заказа;
- откат изменений при ошибке внутри транзакции;
- основные ошибки HTTP API.

## API

### Создание заказа

```http
POST /orders
```

Пример запроса:

```json
{
  "items": [
    {
      "productId": 1,
      "quantity": 2
    },
    {
      "productId": 2,
      "quantity": 1
    }
  ]
}
```

Пример ответа:

```json
{
  "id": 1,
  "items": [
    {
      "productId": 1,
      "quantity": 2,
      "price": 79.99,
      "subtotal": 159.98
    },
    {
      "productId": 2,
      "quantity": 1,
      "price": 39.50,
      "subtotal": 39.50
    }
  ],
  "total": 199.48
}
```

Цена товара всегда берётся из базы данных. Клиент не передаёт цену товара в запросе.

При создании заказа текущая цена товара сохраняется в `order_items`. Поэтому изменение цены товара в будущем не изменит стоимость уже созданного заказа.

### Пример через curl

```bash
curl -X POST http://localhost:8080/orders \
  -H "Content-Type: application/json" \
  -d '{
    "items": [
      {
        "productId": 1,
        "quantity": 2
      },
      {
        "productId": 2,
        "quantity": 1
      }
    ]
  }'
```

### Получение заказа

```http
GET /orders/{id}
```

Пример:

```bash
curl http://localhost:8080/orders/1
```

Если заказ не существует, API возвращает `404 Not Found`.

Пример ответа:

```json
{
  "code": "ORDER_NOT_FOUND",
  "message": "Order 999 not found"
}
```

## Валидация и бизнес-правила

При создании заказа проверяется следующее:

- `items` не должен быть `null`;
- список `items` не должен быть пустым;
- элементы внутри `items` не должны быть `null`;
- `productId` не должен быть `null`;
- `quantity` должен быть больше `0`;
- товар должен существовать;
- товар должен быть доступен;
- товара должно быть достаточно на складе;
- одинаковый `productId` нельзя передавать несколько раз.

Повторяющиеся `productId` отклоняются с ошибкой.

Я выбрал такой вариант вместо объединения одинаковых позиций, чтобы контракт API оставался однозначным, а проверка остатков была проще и понятнее.

## Транзакционность

Создание заказа выполняется внутри одной транзакции.

При обработке заказа уменьшаются остатки товаров.

Если при обработке одной из следующих позиций возникает ошибка, все предыдущие изменения откатываются, а заказ не создаётся.

Это поведение отдельно проверяется интеграционным тестом на реальной PostgreSQL через Testcontainers.

## Работа с денежными значениями

Для хранения и расчётов денежных значений используется `BigDecimal`.

`double` и `float` не используются, так как арифметика с плавающей точкой может приводить к ошибкам точности при работе с деньгами.

В PostgreSQL денежные значения хранятся в колонках типа:

```text
DECIMAL(19,2)
```

## Структура базы данных

Основные таблицы:

```text
products
orders
order_items
```

`order_items` хранит:

- товар;
- количество;
- цену товара на момент создания заказа.

Схема базы данных управляется через Liquibase.

## Структура проекта

```text
controller/   REST-контроллеры
dto/          модели запросов и ответов
entity/       JPA-сущности
exception/    исключения и обработка ошибок API
repository/   Spring Data репозитории
service/      бизнес-логика
```

## Архитектурные решения

Приложение разделено на несколько слоёв:

- `controller` отвечает за HTTP API и валидацию входных данных;
- `service` содержит бизнес-логику создания и получения заказов;
- `repository` отвечает за работу с базой данных через Spring Data JPA;
- `entity` используется как persistence-модель;
- DTO отделяют внешний REST-контракт от JPA-сущностей;
- пакет `exception` содержит бизнес-исключения и единый HTTP error mapping.

Создание заказа выполняется в `OrderService` внутри транзакции, потому что сохранение заказа и изменение остатков должны быть одной атомарной операцией.

Цена товара берётся только из базы данных и сохраняется в `OrderItem` как snapshot цены на момент покупки.

Для повторяющихся `productId` выбрана стратегия reject, а не объединение позиций.

## Что не реализовано и ограничения

Текущая реализация явно не защищает изменение остатков от конкурентного создания заказов.

Например, две параллельные транзакции теоретически могут одновременно прочитать один и тот же остаток товара до фиксации изменений.

Транзакция гарантирует rollback при ошибке внутри одного запроса, но сама по себе не предотвращает такой конкурентный сценарий.

В production-решении для этого можно использовать:

- pessimistic locking;
- optimistic locking через `@Version`;
- атомарный SQL update с проверкой остатка.

В рамках тестового задания дополнительная concurrency-логика не добавлялась, чтобы не усложнять основную реализацию.
